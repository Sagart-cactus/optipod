OptimizationPolicy is the core resource that controls how OptiPod optimizes your workloads. This guide covers everything you need to know about creating effective policies.

## Basic Policy Structure

Every OptimizationPolicy has five main sections:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: my-policy
  namespace: default
spec:
  # 1. Operational mode
  mode: Recommend

  # 2. Workload selector
  selector:
    workloadSelector:
      matchLabels:
        optipod.io/enabled: "true"
    workloadTypes:
      include:
        - Deployment

  # 3. Metrics configuration
  metricsConfig:
    provider: prometheus
    rollingWindow: 7d
    percentile: P90
    safetyFactor: 1.2

  # 4. Resource bounds
  resourceBounds:
    cpu:
      min: 10m
      max: 4000m
    memory:
      min: 64Mi
      max: 8Gi

  # 5. Update strategy
  updateStrategy:
    strategy: webhook
    rolloutStrategy: onNextRestart
```

## Workload Selector

Define which workloads this policy applies to using the `selector` field.

### By Workload Type

Target specific workload types using `workloadTypes`:

```yaml
selector:
  workloadTypes:
    include:
      - Deployment
      - StatefulSet
      - DaemonSet
```

**Supported workload types:**
- `Deployment`
- `StatefulSet`
- `DaemonSet`

You can also exclude specific types:

```yaml
selector:
  workloadTypes:
    include:
      - Deployment
      - StatefulSet
    exclude:
      - DaemonSet
```

### By Label Selector

Use labels to opt-in workloads with `workloadSelector`:

```yaml
selector:
  workloadSelector:
    matchLabels:
      optipod.io/enabled: "true"
      environment: production
```

Or use expressions for more flexibility:

```yaml
selector:
  workloadSelector:
    matchExpressions:
      - key: optipod.io/enabled
        operator: In
        values: ["true"]
      - key: tier
        operator: NotIn
        values: ["critical"]
```

### By Namespace

Use `namespaceSelector` to target workloads in specific namespaces:

```yaml
selector:
  namespaceSelector:
    matchLabels:
      environment: production
```

Or use the `namespaces` allow/deny lists:

```yaml
selector:
  namespaces:
    allow:
      - production
      - staging
    deny:
      - kube-system
      - kube-public
```

:::note
The `deny` list takes precedence over the `allow` list.
:::

### Combined Selectors

Combine multiple selectors for fine-grained control:

```yaml
selector:
  workloadTypes:
    include:
      - Deployment
      - StatefulSet
  workloadSelector:
    matchLabels:
      optipod.io/enabled: "true"
  namespaceSelector:
    matchLabels:
      environment: production
```

## Metrics Configuration

Configure how OptiPod collects and analyzes metrics.

### Provider

OptiPod supports three metrics providers:

```yaml
metricsConfig:
  provider: prometheus  # or "metrics-server" or "custom"
```

**Available providers:**
- `prometheus` - Query Prometheus for historical metrics (recommended)
- `metrics-server` - Use Kubernetes metrics-server (simpler setup)
- `custom` - Custom metrics provider (requires code extension)

### Rolling Window

The `rollingWindow` defines how far back to analyze metrics:

```yaml
metricsConfig:
  rollingWindow: 7d  # 7 days (default: 24h)
```

**Recommendations:**
- **3d**: Fast adaptation, less stable
- **7d**: Balanced (recommended for most workloads)
- **14d**: Very stable, slower adaptation
- **30d**: Maximum stability (for critical workloads)

### Percentile

Choose which percentile to use for recommendations:

```yaml
metricsConfig:
  percentile: P90  # P50, P90, or P99 (default: P90)
```

**Percentile guide:**
- **P50**: Median usage, aggressive optimization
- **P90**: 90th percentile, balanced (recommended)
- **P99**: 99th percentile, conservative

### Safety Factor

The `safetyFactor` is a multiplier applied to the percentile value:

```yaml
metricsConfig:
  safetyFactor: 1.2  # 20% headroom (default: 1.2)
```

**Example:** If P90 CPU usage is 100m and safetyFactor is 1.2, the recommendation will be 120m.

### metrics-server Configuration

When using metrics-server, you can configure minimum samples required:

```yaml
metricsConfig:
  provider: metrics-server
  metricsServer:
    minSamplesRequired: 10  # Minimum samples before recommendations
```

## Resource Bounds

Set minimum and maximum values for recommendations.

### CPU Bounds

```yaml
resourceBounds:
  cpu:
    min: 10m       # Minimum 10 millicores
    max: 4000m     # Maximum 4 cores
```

### Memory Bounds

```yaml
resourceBounds:
  memory:
    min: 64Mi      # Minimum 64 MiB
    max: 8Gi       # Maximum 8 GiB
```

:::caution
Resource bounds apply to all containers. OptiPod does not currently support per-container bounds.
:::

## Update Strategy

Choose how OptiPod applies recommendations.

### Strategy Types

OptiPod supports two update strategies:

```yaml
updateStrategy:
  strategy: webhook  # or "ssa"
```

**Available strategies:**
- `webhook`: Mutating webhook applies resources at pod creation (default, GitOps-safe)
- `ssa`: Server-Side Apply updates workload specs directly

### Rollout Strategy

Control when changes take effect (webhook strategy only):

```yaml
updateStrategy:
  strategy: webhook
  rolloutStrategy: onNextRestart  # or "immediate"
```

**Rollout options:**
- `onNextRestart`: Apply on next pod restart (default, safer)
- `immediate`: Trigger rolling restart immediately

### Server-Side Apply Options

When using SSA strategy:

```yaml
updateStrategy:
  strategy: ssa
  useServerSideApply: true  # Enable SSA (default: true)
  updateRequestsOnly: true  # Only update requests, not limits (default: true)
```

### Limit Configuration

Configure how limits are calculated from requests:

```yaml
updateStrategy:
  limitConfig:
    cpuLimitMultiplier: 1.0      # Limit = request * 1.0 (default: 1.0)
    memoryLimitMultiplier: 1.1   # Limit = request * 1.1 (default: 1.1)
```

### In-Place Resize

Enable in-place pod resize when supported by Kubernetes:

```yaml
updateStrategy:
  allowInPlaceResize: true   # Enable in-place resize (default: true)
  allowRecreate: false       # Allow pod recreation if resize fails (default: false)
```

### Memory Safety

Control memory decrease behavior:

```yaml
updateStrategy:
  allowUnsafeMemoryDecrease: false  # Block unsafe memory decreases (default: false)
```

:::warning
Setting `allowUnsafeMemoryDecrease: true` disables memory safety checks. Use with caution!
:::

### Gradual Memory Decrease

Enable gradual memory reduction for safer optimization:

```yaml
updateStrategy:
  gradualDecreaseConfig:
    enabled: true
    memoryDecreasePercentage: 10        # Decrease by 10% per reconciliation (default: 10)
    minimumDecreaseThreshold: 100Mi     # Only gradual if decrease > 100Mi
    maximumTotalDecrease: 70            # Max 70% total decrease (default: 70)
```

## Policy Weight

When multiple policies match the same workload, the policy with the highest weight wins:

```yaml
spec:
  weight: 200  # Higher weight = higher priority (default: 100, range: 1-1000)
```

## Reconciliation Interval

Control how often the policy is evaluated:

```yaml
spec:
  reconciliationInterval: 5m  # Evaluate every 5 minutes (default: 5m)
```

## Complete Examples

### Example 1: GitOps-Friendly Policy

For teams using ArgoCD or Flux:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: gitops-policy
  namespace: production
spec:
  mode: Recommend  # Manual application via GitOps
  weight: 100

  selector:
    workloadTypes:
      include:
        - Deployment
        - StatefulSet
    workloadSelector:
      matchLabels:
        optipod.io/enabled: "true"

  metricsConfig:
    provider: prometheus
    rollingWindow: 14d  # Stable recommendations
    percentile: P90
    safetyFactor: 1.2

  resourceBounds:
    cpu:
      min: 10m
      max: 4000m
    memory:
      min: 128Mi
      max: 8Gi

  updateStrategy:
    strategy: webhook
    rolloutStrategy: onNextRestart
```

### Example 2: Auto-Optimization Policy

For production workloads with Auto mode:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: auto-policy
  namespace: production
spec:
  mode: Auto
  weight: 150

  selector:
    workloadTypes:
      include:
        - Deployment
    workloadSelector:
      matchLabels:
        optipod.io/enabled: "true"
        tier: "frontend"

  metricsConfig:
    provider: prometheus
    rollingWindow: 7d
    percentile: P90
    safetyFactor: 1.2

  resourceBounds:
    cpu:
      min: 50m
      max: 2000m
    memory:
      min: 128Mi
      max: 4Gi

  updateStrategy:
    strategy: ssa
    useServerSideApply: true
    updateRequestsOnly: true
    allowUnsafeMemoryDecrease: false
    gradualDecreaseConfig:
      enabled: true
      memoryDecreasePercentage: 10
      minimumDecreaseThreshold: 100Mi
      maximumTotalDecrease: 70
```

### Example 3: Development Environment

For non-production with aggressive optimization:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: dev-policy
  namespace: development
spec:
  mode: Auto
  weight: 100

  selector:
    workloadTypes:
      include:
        - Deployment
        - StatefulSet
    workloadSelector:
      matchLabels:
        optipod.io/enabled: "true"

  metricsConfig:
    provider: metrics-server
    rollingWindow: 3d  # Faster adaptation
    percentile: P90
    safetyFactor: 1.1  # Less headroom
    metricsServer:
      minSamplesRequired: 5

  resourceBounds:
    cpu:
      min: 10m
      max: 1000m
    memory:
      min: 32Mi
      max: 2Gi

  updateStrategy:
    strategy: ssa
    allowUnsafeMemoryDecrease: true  # Less strict for dev
```

### Example 4: Multi-Tier Policy

Different settings for different tiers:

```yaml
# Critical tier - conservative
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: critical-policy
  namespace: production
spec:
  mode: Recommend
  weight: 200  # Higher priority

  selector:
    workloadSelector:
      matchLabels:
        tier: critical

  metricsConfig:
    provider: prometheus
    rollingWindow: 30d  # Very stable
    percentile: P99     # Conservative
    safetyFactor: 1.5   # Extra headroom

  resourceBounds:
    cpu:
      min: 100m
      max: 8000m
    memory:
      min: 256Mi
      max: 16Gi

  updateStrategy:
    strategy: webhook
    rolloutStrategy: onNextRestart
---
# Standard tier - balanced
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: standard-policy
  namespace: production
spec:
  mode: Auto
  weight: 100

  selector:
    workloadSelector:
      matchLabels:
        tier: standard

    provider: prometheus
    rollingWindow: 7d
    percentile: P90
    safetyFactor: 1.2

    cpu:
      min: 10m
      max: 4000m
    memory:
      min: 64Mi
      max: 8Gi

  updateStrategy:
    strategy: ssa
    gradualDecreaseConfig:
      enabled: true
```

## Policy Management

### Create Policy

```bash
kubectl apply -f policy.yaml
```

### View Policies

```bash
# List all policies
kubectl get optimizationpolicy -A

# View specific policy
kubectl get optimizationpolicy my-policy -n production -o yaml

# Describe policy
kubectl describe optimizationpolicy my-policy -n production
```

### Update Policy

```bash
# Edit interactively
kubectl edit optimizationpolicy my-policy -n production

# Patch specific fields
kubectl patch optimizationpolicy my-policy -n production \
  --type merge \
  -p '{"spec":{"mode":"Auto"}}'
```

### Delete Policy

```bash
kubectl delete optimizationpolicy my-policy -n production
```

:::caution
Deleting a policy stops optimization for affected workloads. Existing recommendations remain as annotations.
:::

## Best Practices

1. **Start with Recommend mode**: Build confidence before Auto mode
2. **Use long rolling windows**: 7-14 days for stable recommendations
3. **Set appropriate bounds**: Prevent unrealistic recommendations
4. **Label selectively**: Opt-in workloads gradually
5. **Use policy weights**: Different priorities for different tiers
6. **Enable gradual decrease**: Safer memory optimization
7. **Document policies**: Add annotations explaining the configuration
8. **Version control**: Store policies in Git
9. **Test in non-prod**: Validate policies before production

## Troubleshooting

### No Recommendations Generated

Check:
- Workload has correct labels matching `workloadSelector`
- Policy targets correct workload types
- Sufficient metrics data available (check `rollingWindow`)
- Metrics provider is accessible

### Recommendations Seem Wrong

Adjust:
- `rollingWindow` (longer = more stable)
- `percentile` (P99 = more conservative)
- `safetyFactor` (higher = more headroom)
- `resourceBounds` (may be too restrictive)

### Policy Not Applying Changes

Verify:
- Mode is set to `Auto`
- Update strategy is configured correctly
- `allowUnsafeMemoryDecrease` setting if memory is decreasing
- Check policy status: `kubectl describe optimizationpolicy <name>`
