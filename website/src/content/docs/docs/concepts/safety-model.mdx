title: Safety Model

OptiPod is designed with safety as a top priority. Multiple layers of protection ensure that resource optimizations don't cause outages or performance degradation.

## Safety Principles

1. **Recommend by default**: No automatic changes without explicit opt-in
2. **Bounded recommendations**: Hard limits prevent extreme values
3. **Gradual memory reduction**: Large decreases applied incrementally
4. **Memory safety checks**: Prevent dangerous memory reductions
5. **Transparent operation**: Clear visibility into all changes

## Safety Layers

### Layer 1: Operational Modes

OptiPod has three operational modes, with safety increasing from Auto to Disabled:

**Recommend Mode (Safest)**
- OptiPod only creates recommendations as annotations
- No automatic changes to workloads
- You review and apply changes manually
- Perfect for GitOps workflows

**Auto Mode**
- OptiPod automatically applies recommendations
- Requires explicit opt-in via `mode: Auto`
- Subject to all safety constraints
- Use after building confidence in Recommend mode

**Disabled Mode**
- OptiPod stops processing the workload
- Existing recommendations remain
- Use for emergency situations

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: safe-policy
spec:
  mode: Recommend  # Start here, move to Auto when ready
```

### Layer 2: Resource Bounds

Hard limits on resource values prevent extreme recommendations.

```yaml
spec:
  resourceBounds:
    cpu:
      min: 10m      # Never recommend less than 10m
      max: 4000m    # Never recommend more than 4 cores
    memory:
      min: 64Mi     # Never recommend less than 64Mi
      max: 8Gi      # Never recommend more than 8Gi
```

**Protection:**
- Prevents recommendations below minimum viable resources
- Prevents wasteful over-provisioning
- Customizable per policy
- Applied to all containers

**Example:**
```
Calculated recommendation: 5m CPU
After bounds: 10m CPU (clamped to minimum)

Calculated recommendation: 16Gi memory
After bounds: 8Gi memory (clamped to maximum)
```

### Layer 3: Safety Factor

The safety factor adds headroom above observed usage to prevent resource exhaustion.

```yaml
spec:
  metricsConfig:
    percentile: P90        # Use 90th percentile
    safetyFactor: 1.2      # Add 20% headroom
```

**How it works:**
```
Observed P90 CPU: 200m
Safety factor: 1.2
Recommendation: 200m × 1.2 = 240m
```

**Protection:**
- Accounts for usage spikes
- Provides buffer for unexpected load
- Configurable per policy (minimum 1.0)

**Recommended values:**
- **1.1** (10% headroom): Aggressive optimization, stable workloads
- **1.2** (20% headroom): Balanced, recommended for most workloads
- **1.5** (50% headroom): Conservative, critical workloads

### Layer 4: Memory Safety Checks

OptiPod includes special protection for memory to prevent OOM kills.

#### Allow Unsafe Memory Decrease

By default, OptiPod blocks memory decreases that could cause issues:

```yaml
spec:
  updateStrategy:
    allowUnsafeMemoryDecrease: false  # Default: block unsafe decreases
```

**When set to `false` (default):**
- OptiPod analyzes memory decrease safety
- Blocks decreases that could cause OOM kills
- Logs warnings about blocked decreases

**When set to `true`:**
- All memory recommendations are applied
- Use with caution in production
- Recommended only for development environments

:::warning
Setting `allowUnsafeMemoryDecrease: true` disables memory safety checks. Use only when you understand the risks.
:::

#### Gradual Memory Decrease

For safer memory optimization, enable gradual decrease:

```yaml
spec:
  updateStrategy:
    gradualDecreaseConfig:
      enabled: true
      memoryDecreasePercentage: 10        # Decrease by 10% per reconciliation
      minimumDecreaseThreshold: 100Mi     # Only gradual if decrease > 100Mi
      maximumTotalDecrease: 70            # Max 70% total decrease
```

**How it works:**

```
Current memory: 1000Mi
Target memory: 400Mi (60% decrease)

Reconciliation 1: 1000Mi → 900Mi (10% decrease)
Wait for reconciliationInterval (e.g., 5 minutes)
Reconciliation 2: 900Mi → 810Mi (10% decrease)
Wait...
Reconciliation 3: 810Mi → 729Mi (10% decrease)
Continue until reaching 400Mi
```

**Protection:**
- Large decreases applied incrementally
- Time to observe effects between steps
- Can stop if issues detected
- Respects `maximumTotalDecrease` limit

**Configuration:**

- **memoryDecreasePercentage**: Max decrease per reconciliation (1-50%, default 10%)
- **minimumDecreaseThreshold**: Decreases smaller than this are applied immediately
- **maximumTotalDecrease**: Max total decrease from original value (1-90%, default 70%)

### Layer 5: Percentile Selection

Choose which percentile to use for recommendations:

```yaml
spec:
  metricsConfig:
    percentile: P90  # P50, P90, or P99
```

**Percentile guide:**
- **P50** (median): Aggressive optimization, may not handle spikes
- **P90**: Balanced, handles most spikes (recommended)
- **P99**: Conservative, handles nearly all spikes

**Example:**
```
P50 CPU usage: 100m
P90 CPU usage: 200m
P99 CPU usage: 300m

With P90 and safetyFactor 1.2:
Recommendation: 200m × 1.2 = 240m
```

### Layer 6: Rolling Window

The rolling window determines how much historical data is used:

```yaml
spec:
  metricsConfig:
    rollingWindow: 7d  # 7 days of data
```

**Recommendations:**
- **3d**: Fast adaptation, less stable
- **7d**: Balanced (recommended)
- **14d**: Very stable, slower adaptation
- **30d**: Maximum stability for critical workloads

**Protection:**
- Longer windows = more stable recommendations
- Shorter windows = faster adaptation to changes
- Filters out temporary anomalies

## Safety Configurations

### Conservative (Production Critical)

Safest settings for critical production workloads:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: conservative-policy
spec:
  mode: Recommend  # Manual approval required
  weight: 200      # High priority

  metricsConfig:
    provider: prometheus
    rollingWindow: 30d      # Very stable
    percentile: P99         # Conservative
    safetyFactor: 1.5       # 50% headroom

  resourceBounds:
    cpu:
      min: 100m
      max: 8000m
    memory:
      min: 256Mi
      max: 16Gi

  updateStrategy:
    strategy: webhook
    rolloutStrategy: onNextRestart
    allowUnsafeMemoryDecrease: false
```

### Balanced (Production Standard)

Moderate safety for standard production workloads:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: balanced-policy
spec:
  mode: Auto  # Automatic application
  weight: 100

  metricsConfig:
    provider: prometheus
    rollingWindow: 7d       # Balanced
    percentile: P90         # Recommended
    safetyFactor: 1.2       # 20% headroom

  resourceBounds:
    cpu:
      min: 10m
      max: 4000m
    memory:
      min: 64Mi
      max: 8Gi

  updateStrategy:
    strategy: ssa
    allowUnsafeMemoryDecrease: false
    gradualDecreaseConfig:
      enabled: true
      memoryDecreasePercentage: 10
      minimumDecreaseThreshold: 100Mi
      maximumTotalDecrease: 70
```

### Aggressive (Development/Staging)

Faster optimization for non-critical workloads:

```yaml
apiVersion: optipod.optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: aggressive-policy
spec:
  mode: Auto
  weight: 100

  metricsConfig:
    provider: metrics-server
    rollingWindow: 3d       # Fast adaptation
    percentile: P90
    safetyFactor: 1.1       # 10% headroom

  resourceBounds:
    cpu:
      min: 10m
      max: 2000m
    memory:
      min: 32Mi
      max: 4Gi

  updateStrategy:
    strategy: ssa
    allowUnsafeMemoryDecrease: true  # Less strict for dev
    gradualDecreaseConfig:
      enabled: false  # Immediate changes
```

:::caution
Aggressive settings increase risk. Only use for non-critical workloads where you can tolerate occasional issues.
:::

## Safety Scenarios

### Scenario 1: Insufficient Metrics Data

**Situation:** New workload with only 1 day of metrics, rolling window is 7 days

**OptiPod behavior:**
- Waits for sufficient data
- No recommendation generated yet
- Logs indicate waiting for more samples

**Resolution:** Wait for rolling window period to collect data

### Scenario 2: Large Memory Decrease Needed

**Situation:** Current: 2Gi memory, Optimal: 500Mi (75% decrease)

**With gradual decrease enabled:**
```
Reconciliation 1: 2Gi → 1.8Gi (10% decrease)
Wait 5 minutes (reconciliationInterval)
Reconciliation 2: 1.8Gi → 1.62Gi (10% decrease)
Wait 5 minutes
Reconciliation 3: 1.62Gi → 1.46Gi (10% decrease)
...continue until reaching 500Mi
```

**Protection:** Gradual changes allow monitoring at each step

### Scenario 3: Memory Decrease Blocked

**Situation:** OptiPod calculates a memory decrease that could cause OOM

**OptiPod behavior:**
- Safety check detects risk
- Blocks the decrease
- Logs warning: "Memory decrease blocked by safety check"
- Recommendation not applied

**Resolution:**
- Review actual memory usage
- Adjust resource bounds if needed
- Enable `allowUnsafeMemoryDecrease` only if you're certain it's safe

### Scenario 4: Recommendation Outside Bounds

**Situation:** Calculated recommendation is 5m CPU, but min bound is 10m

**OptiPod behavior:**
- Clamps recommendation to 10m
- Applies bounded value
- Logs indicate clamping occurred

**Protection:** Prevents unrealistic resource values

## Monitoring Safety

### Check Policy Status

```bash
kubectl describe optimizationpolicy my-policy
```

Look for:
```yaml
Status:
  Conditions:
    Type:    Ready
    Status:  True
    Message: Policy is active and processing workloads
  Workloads Discovered:  5
  Workloads Processed:   5
```

### Monitor Workload Health

```bash
# Check for OOM kills
kubectl get events --field-selector reason=OOMKilled --sort-by='.lastTimestamp'

# Check pod restarts
kubectl get pods -l app=my-app -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[*].restartCount}{"\n"}{end}'

# Check resource usage
kubectl top pod -l app=my-app
```

### Review Recommendations

```bash
# Get all OptiPod annotations
kubectl get deployment my-app -o json | \
  jq '.metadata.annotations | with_entries(select(.key | startswith("optipod.io/")))'

# Check last recommendation time
kubectl get deployment my-app \
  -o jsonpath='{.metadata.annotations.optipod\.io/last-recommendation}'
```

## Best Practices

1. **Start with Recommend mode**: Build confidence before Auto mode
2. **Use appropriate percentiles**: P90 for most workloads, P99 for critical
3. **Set realistic bounds**: Based on actual workload requirements
4. **Enable gradual decrease**: For safer memory optimization
5. **Monitor closely**: Watch for issues after enabling Auto mode
6. **Test in non-prod**: Validate settings before production
7. **Document decisions**: Note why you chose specific safety settings

## Emergency Procedures

### If OptiPod Causes Issues

1. **Immediate**: Switch policy to Disabled mode
```bash
kubectl patch optimizationpolicy my-policy --type merge \
  -p '{"spec":{"mode":"Disabled"}}'
```

2. **Revert changes**: Manually restore previous resource values
```bash
kubectl set resources deployment my-app \
  --requests=cpu=1000m,memory=1Gi \
  --limits=cpu=2000m,memory=2Gi
```

3. **Investigate**: Review logs and recommendations
```bash
kubectl logs -n optipod-system -l app.kubernetes.io/name=optipod --tail=100
```

4. **Adjust policy**: Update safety settings
5. **Test**: Re-enable in Recommend mode
6. **Monitor**: Watch closely before returning to Auto mode

## Understanding Trade-offs

### Safety vs Optimization

More safety = less aggressive optimization:

| Setting | Safety | Optimization | Use Case |
|---------|--------|--------------|----------|
| P99 + 1.5x safety factor | Highest | Lowest | Critical production |
| P90 + 1.2x safety factor | Balanced | Balanced | Standard production |
| P50 + 1.1x safety factor | Lower | Highest | Development |

### Speed vs Stability

| Rolling Window | Adaptation Speed | Stability | Use Case |
|----------------|------------------|-----------|----------|
| 3 days | Fast | Lower | Development |
| 7 days | Balanced | Good | Standard production |
| 14-30 days | Slow | Highest | Critical workloads |
