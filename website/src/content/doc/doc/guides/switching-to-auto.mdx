---
title: Switching to Auto Mode
description: How to safely transition from Recommend to Auto mode
---

Auto mode allows OptiPod to automatically apply resource recommendations with safety guardrails. This guide walks you through the transition from manual Recommend mode to automated Auto mode.

## Prerequisites

Before switching to Auto mode, ensure:

- ✅ OptiPod has been running in Recommend mode for 2+ weeks
- ✅ You've reviewed and manually applied several recommendations
- ✅ Manual applications have been successful
- ✅ You understand the safety model
- ✅ Monitoring is in place to detect issues

## Readiness Checklist

### 1. Review Historical Recommendations

Check that recommendations have been accurate:

```bash
# Review all recommendations
kubectl get deployments -l optipod.io/enabled=true -A \
  -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}: {.metadata.annotations.optipod\.io/recommendation}{"\n"}{end}' | \
  jq -r '. | select(. != null)'
```

**Questions to ask:**
- Have recommendations been consistently reasonable?
- Did manually applied recommendations work well?
- Are confidence levels mostly "high"?

### 2. Verify Safety Configuration

Ensure your policy has appropriate safety settings:

```bash
kubectl get optimizationpolicy <policy-name> -o yaml
```

Look for:
```yaml
safetyConfig:
  confidenceThreshold: high
  maxChangePercent: 50
  minUpdateInterval: 24h
  memoryFloor: 64Mi
  memoryHeadroom: 20%
  enableRollback: true
```

### 3. Check Monitoring

Verify you can monitor:
- Pod status and restarts
- Resource usage (kubectl top)
- Application metrics (latency, errors)
- OOM kills and crashes

### 4. Prepare Rollback Plan

Document how to quickly revert:

```bash
# Save current policy
kubectl get optimizationpolicy <policy-name> -o yaml > policy-backup.yaml

# Know how to disable
kubectl patch optimizationpolicy <policy-name> \
  --type merge \
  -p '{"spec":{"mode":"Disabled"}}'
```

## Transition Strategy

### Phase 1: Single Non-Critical Workload

Start with one low-risk workload.

#### Step 1: Create Test Policy

```yaml
apiVersion: optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: auto-test-policy
  namespace: development
spec:
  mode: Auto
  updateStrategy: ServerSideApply

  targetWorkloads:
    kinds:
      - Deployment
    labelSelector:
      matchLabels:
        optipod.io/auto-test: "true"  # Specific label for testing

  metricsConfig:
    provider: prometheus
    lookbackWindow: 7d

  resourceBounds:
    cpu:
      min: 10m
      max: 2000m
    memory:
      min: 64Mi
      max: 4Gi

  safetyConfig:
    confidenceThreshold: high
    maxChangePercent: 50
    minUpdateInterval: 24h
    memoryFloor: 64Mi
    memoryHeadroom: 20%
    enableRollback: true
```

#### Step 2: Label Test Workload

```bash
kubectl label deployment test-app optipod.io/auto-test=true
```

#### Step 3: Monitor for 1 Week

Watch the test workload closely:

```bash
# Check for updates
kubectl get deployment test-app -o yaml | grep optipod.io/last-applied

# Monitor resource usage
kubectl top pod -l app=test-app

# Check for issues
kubectl get events --field-selector involvedObject.name=test-app

# Review logs
kubectl logs -l app=test-app --tail=100
```

#### Step 4: Evaluate Results

After 1 week, assess:
- Were changes applied successfully?
- Did the workload remain stable?
- Were there any OOM kills or crashes?
- Did performance remain acceptable?

### Phase 2: Expand to Non-Critical Workloads

If Phase 1 succeeded, expand gradually.

#### Step 1: Update Policy Selector

```yaml
targetWorkloads:
  labelSelector:
    matchLabels:
      optipod.io/enabled: "true"
      tier: "non-critical"
```

#### Step 2: Label Additional Workloads

```bash
# Label multiple workloads
kubectl label deployment app1 app2 app3 tier=non-critical
```

#### Step 3: Monitor for 2 Weeks

Track all affected workloads:

```bash
# List all workloads in Auto mode
kubectl get deployments -l tier=non-critical -o wide

# Check for any issues
kubectl get events --field-selector reason=OOMKilled
kubectl get events --field-selector reason=CrashLoopBackOff
```

### Phase 3: Production Workloads

After 2+ weeks of successful Auto mode on non-critical workloads.

#### Step 1: Create Production Policy

```yaml
apiVersion: optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: production-auto-policy
  namespace: production
spec:
  mode: Auto
  updateStrategy: ServerSideApply

  targetWorkloads:
    kinds:
      - Deployment
      - StatefulSet
    labelSelector:
      matchLabels:
        optipod.io/enabled: "true"
        tier: "production"

  metricsConfig:
    provider: prometheus
    lookbackWindow: 14d  # Longer for production

  resourceBounds:
    cpu:
      min: 50m
      max: 4000m
    memory:
      min: 128Mi
      max: 8Gi

  safetyConfig:
    confidenceThreshold: high
    maxChangePercent: 25  # More conservative
    minUpdateInterval: 48h  # Slower updates
    memoryFloor: 128Mi
    memoryHeadroom: 30%  # More headroom
    enableRollback: true
    rollbackTriggers:
      - oomKills
      - crashLoops
      - highErrorRate
```

#### Step 2: Gradual Rollout

Don't enable all production workloads at once:

```bash
# Week 1: 10% of production workloads
kubectl label deployment prod-app1 prod-app2 tier=production

# Week 2: 25% of production workloads
kubectl label deployment prod-app3 prod-app4 prod-app5 tier=production

# Week 3: 50% of production workloads
# ... continue gradually

# Week 6+: All production workloads
```

#### Step 3: Enhanced Monitoring

Set up alerts for:
- OOM kills
- Pod restarts
- High error rates
- Latency increases
- OptiPod rollbacks

### Phase 4: Critical Workloads

Only after months of successful Auto mode on production.

#### Step 1: Extra Conservative Policy

```yaml
apiVersion: optipod.io/v1alpha1
kind: OptimizationPolicy
metadata:
  name: critical-auto-policy
  namespace: production
spec:
  mode: Auto
  updateStrategy: ServerSideApply

  targetWorkloads:
    labelSelector:
      matchLabels:
        tier: "critical"

  metricsConfig:
    lookbackWindow: 30d  # Maximum stability

  safetyConfig:
    confidenceThreshold: high
    maxChangePercent: 15  # Very conservative
    minUpdateInterval: 168h  # Weekly updates only
    memoryFloor: 256Mi
    memoryHeadroom: 50%  # Extra headroom
    enableRollback: true
```

#### Step 2: One at a Time

Enable Auto mode for critical workloads one at a time with weeks between each.

## Monitoring Auto Mode

### Daily Checks

```bash
# Check for any rollbacks
kubectl get optimizationpolicy -A -o json | \
  jq -r '.items[] | select(.status.rollbackCount > 0) |
    "\(.metadata.namespace)/\(.metadata.name): \(.status.rollbackCount) rollbacks"'

# Check for recent updates
kubectl get deployments -A -l optipod.io/enabled=true \
  -o jsonpath='{range .items[*]}{.metadata.namespace}/{.metadata.name}: {.metadata.annotations.optipod\.io/last-applied}{"\n"}{end}'

# Check for OOM kills
kubectl get events -A --field-selector reason=OOMKilled --sort-by='.lastTimestamp'
```

### Weekly Review

```bash
# Generate report of all Auto mode changes
kubectl get events -A --field-selector involvedObject.kind=OptimizationPolicy | \
  grep "Applied recommendation"

# Review resource usage trends
kubectl top pods -A -l optipod.io/enabled=true

# Check policy status
kubectl get optimizationpolicy -A -o yaml
```

## Handling Issues

### If OptiPod Causes Problems

#### Immediate Response

```bash
# Disable Auto mode immediately
kubectl patch optimizationpolicy <policy-name> \
  --type merge \
  -p '{"spec":{"mode":"Disabled"}}'

# Revert problematic workload
kubectl set resources deployment <name> \
  --requests=cpu=<previous>,memory=<previous>
```

#### Investigation

```bash
# Check what changed
kubectl get deployment <name> -o yaml | grep optipod.io/

# Review operator logs
kubectl logs -n optipod-system -l app=optipod-operator --tail=500

# Check policy configuration
kubectl get optimizationpolicy <policy-name> -o yaml
```

#### Resolution

1. Identify root cause
2. Adjust policy settings
3. Test in Recommend mode
4. Re-enable Auto mode with updated settings

### Common Issues

**Issue: Frequent OOM Kills**

Solution:
```yaml
safetyConfig:
  memoryFloor: 256Mi  # Increase floor
  memoryHeadroom: 40%  # Increase headroom
```

**Issue: Too Many Changes**

Solution:
```yaml
safetyConfig:
  minUpdateInterval: 72h  # Slow down updates
  maxChangePercent: 25  # Smaller changes
```

**Issue: Low Confidence Recommendations**

Solution:
```yaml
metricsConfig:
  lookbackWindow: 21d  # Longer window
safetyConfig:
  confidenceThreshold: high  # Stricter threshold
```

## Best Practices

1. **Go slow**: Take months, not weeks
2. **Monitor closely**: Especially in first few weeks
3. **Start conservative**: Tighten safety settings initially
4. **Document everything**: Track what works and what doesn't
5. **Have rollback ready**: Know how to quickly disable
6. **Communicate**: Inform team about Auto mode rollout
7. **Review regularly**: Weekly review of Auto mode activity
8. **Adjust policies**: Fine-tune based on experience

## Success Criteria

You've successfully transitioned to Auto mode when:

- ✅ No OOM kills or crashes caused by OptiPod
- ✅ Resource usage remains stable
- ✅ Application performance unchanged
- ✅ Measurable cost savings achieved
- ✅ Team confident in Auto mode
- ✅ Minimal manual intervention needed
