OptiPod workload optimization

Feature-by-feature comparison of the original OptiPod checkout and this implementation. Scope covers workload resources, application safety and reporting. Node provisioning, bin packing and node purchasing are outside this project.

Local validation passed: 96 E2E tests, zero failures. Unit/envtest, race-detector, lint and Helm checks also passed. The complete run used the frozen controller implementation on Kubernetes 1.35 in Podman/Kind. A subsequent migration-only cleanup passed its focused E2E rerun. DPV2 application acceptance belongs to the documented canary rollout. See the validation record.

Configuration examples

The migration examples cover two explicit profiles. qa-stability-1 uses CPU P99 / memory maximum, 10% / 10% overhead, seven-day history, a two-minute startup period and immediate application. qa-resiliency-1 uses CPU P95 / memory maximum, 15% / 20% overhead and deferred application, with the same history/startup settings. Both use no CPU limit and Automatic memory limits. Source confidence is not converted into an OptiPod coverage setting.

Example resource bounds are illustrative and require workload-specific review. Choose startup behavior and independent data-quality gates explicitly before generating a policy.

Behavior to review during migration

  • Statistics: OptiPod pools eligible observations across owned replicas and supports five explicit percentile choices. Review the aggregation method and sampling windows when translating an existing profile.
  • Confidence: observed-time coverage and minimum history are data-quality gates, independent of any source confidence score.
  • Deferred application: OptiPod’s onNextRestart waits for natural admission. It does not resize running pods in this mode. The translator includes a review note for the source apply behavior.
  • Forecasting: the OptiPod implementation is a bounded upward linear CPU forecast, without seasonal prediction. JVM support requires existing gauges; it does not inject instrumentation or rewrite JVM flags.
  • Horizontal scaling: OptiPod uses native HPA behavior and protects utilization requests. External/object/custom metrics require the corresponding Kubernetes metrics adapter. It does not convert existing foreign HPAs.
  • Constraints: OptiPod rejects unsafe plans rather than silently changing policy intent to fit quotas. Pod-level resource budgets are not supported. Unknown destination nodes are left unchanged, and existing DaemonSet pods retain their resources.
  • Rollback: exact restoration requires the latest bound action with matching identities and no conflicting edits. Node-specific admission receipts are history, not a uniform workload rollback target.
  • Unsupported configuration options: original limit/request ratios, CPU semi-automatic limits, startup CPU boosting, arbitrary custom controller kinds and automatic instrumentation are not implemented. They were outside the agreed P0–P2 feature set and must not be silently imported.

History storage

Namespaced ConfigMaps retain recent decision transitions, policy snapshots and before/after resource plans across controller restarts and workload deletion. Git should retain declared settings; a proposed GCS archive would preserve records beyond namespace/cluster deletion. See the history design and retention limits.

Validation and rollout

The local environment uses Podman, a private two-node Kind cluster, Kubernetes 1.35, real Prometheus and metrics-server, real KEDA and Argo Rollouts, a real JVM, CPU/memory load generators and deliberate OOM workloads. Resize checks assert unchanged pod UIDs, zero restarts and kubelet-allocated resources. Prometheus and metrics-server are tested independently; retained Prometheus history and metrics-server’s in-memory warm-up are different behaviors.

  1. Use the development commands to reproduce the complete suite or a focused Tilt loop.
  2. Translate effective profiles using the migration guide, then review namespace selectors, explicit bounds, startup treatment and source differences.
  3. Start DPV2 in Recommend with retained Prometheus history covering representative peaks. Select a small, explicit canary set.
  4. Give each canary one resource writer. Disable existing workload automation for that canary before enabling OptiPod Auto.
  5. Check application reliability, PDBs, quotas, HPA/KEDA behavior, OOM recovery and rollback before expanding. Lower requests alone do not establish monetary savings when node provisioning is unchanged.
